# 01 · Overview & Architecture

## 1. Business goal (from `AI descriptions requirements.pdf`)

The product brief ("Internet Securities Limited — AI descriptions: brief requirements") asks for
**corporate-database business descriptions** for companies based in a given country. The required
output is a 3-column table:

1. **Company name (English)** — exactly as provided in the input.
2. **Website homepage URL** — the official, responsive homepage; `–` if it cannot be found.
3. **Descriptions** — one in the country language (`Website_Company_Descirption_AI`) and one in
   English (`Website_Company_Descirption_Translated_AI`).

Key rules from the brief that the code tries to honor:

- Use the company's **official website** as the primary source; fall back to credible public
  sources only if the site can't be found.
- Descriptions: **≥ 250 characters** when meaningful info exists, formal/neutral corporate tone,
  **plain text only** (no headers, links, citations, or hedging phrases), **ASCII only** in the
  English version (strip diacritics).
- If no meaningful public info exists, the description is a single dash `–`.
- **Preserve input order.**

The repository implements this as an automated, queue-based batch service. The bilingual
description requirement is fulfilled by the **Gemini batch post-processing** step
(see [05.pipelines-and-flow.md](05.pipelines-and-flow.md)); the per-row pipeline focuses on
finding the URL and basic firmographics.

> The brief's fields `Website_Company_Descirption_AI` / `_Translated_AI` map directly to the
> result keys `website_company_descirption_ai` / `website_company_descirption_translated_ai`
> (the misspelling "Descirption" is carried through the codebase intentionally — see
> [03.data-models.md](03.data-models.md)).

## 3. The five pipelines

An upload's `pipeline` field selects how each row is processed. All five share the same
queue/worker/state machinery; they differ only in which `execute_*` function the worker calls
(`app.py:5955`–`5996`).

| Pipeline constant (`app.py:121`) | Value | Endpoint | Worker function | Purpose |
|---|---|---|---|---|
| `PIPELINE_FULL` | `full` | `POST /uploads` | `execute_company_lookup(..., include_firmographics=True)` | Full URL discovery **+** firmographics; the only pipeline eligible for Gemini batch post-processing. |
| `PIPELINE_URL_DISCOVERY` | `url_discovery` | `POST /uploads/url-discovery` | `execute_company_lookup(..., include_firmographics=False)` | Find the URL only; skip firmographic enrichment. |
| `PIPELINE_FIRMOGRAPHICS` | `firmographics` | `POST /uploads/firmographics` | `execute_firmographic_extraction(...)` | Input already has the URL; extract firmographics from SerpWow AI-overview. |
| `PIPELINE_GMAPS` | `gmaps` | `POST /uploads/gmaps` | `execute_gmaps_lookup(...)` | Google-Maps-only lookup (website + address + phone + category). |
| `PIPELINE_GSEARCH` | `gsearch` | `POST /uploads/gsearch` | `execute_gsearch_lookup_for_worker(..., phase=…)` | Run a *specific* search-query phase (phase1…phase5/fallback/all) and just collect candidate URLs — a diagnostic/experimentation pipeline. |

See [05.pipelines-and-flow.md](05.pipelines-and-flow.md) for each algorithm in detail.

## 4. Process / deployment topology

The system is designed to run as **two separate processes** that share RabbitMQ + S3:

```
            ┌──────────────────────────────────────────────────────────────┐
            │  API process:  python app.py   (or: uvicorn app:app)          │
            │  ─ Serves the UI + all HTTP endpoints                          │
            │  ─ Parses CSV uploads, writes state.json, PUBLISHES jobs       │
            │  ─ Runs Gemini batch tasks (asyncio tasks in-process)          │
            │  ─ By default it is PRODUCER-ONLY (no consumers)               │
            └──────────────────────────────────────────────────────────────┘
                       │ publish (1 msg/row)                ▲ read/write
                       ▼                                    │  state.json, output.json,
            ┌─────────────────────┐                ┌────────┴───────────┐  batch artifacts,
            │      RabbitMQ        │                │     AWS S3 bucket   │  per-row raw JSON
            │ exchange: singleRA_  │                │ prefix single_ra_  │
            │   search (direct)    │                │   isi/<upload_id>/ │
            │ queue: singleRA_     │                └────────┬───────────┘
            │   search_jobs        │                         │
            └─────────┬───────────┘                         │  (also mirrored to
                      │ consume                              │   /tmp/single_ra_isi/)
                      ▼                                      │
            ┌──────────────────────────────────────────────────────────────┐
            │  Worker process:  python worker.py                             │
            │  ─ N consumers (WORKER_CONCURRENCY) via queue.iterator()       │
            │  ─ For each job runs the pipeline's execute_* function         │
            │  ─ Calls SerpWow + Gemini, writes results into state.json      │
            └──────────────────────────────────────────────────────────────┘
                      │  outbound HTTPS
                      ▼
       SerpWow API (search, ai_overview, places, place_details) ─┐
       Google Gemini API (generateContent / batchGenerateContent)┘
```

- The API and worker both `import app`, so they share **all** of `app.py`'s code and module-level
  globals — but in separate OS processes those globals are **not shared** (each process has its
  own RabbitMQ connection, its own `s3_client`, its own `upload_active_rows`, etc.). This split is
  why the stale/orphan auto-finalizers default to *off* unless the embedded worker is enabled
  (`app.py:5709`–`5720`); in split mode the API can't see the worker's in-memory "active rows".
- **Embedded mode:** set `ENABLE_EMBEDDED_WORKER=true` and the API process *also* starts the
  consumers at startup (`app.py:6246`), so a single process does everything. Used for local dev.
- `worker.py` calls `app.startup_event()` (which connects RabbitMQ) and then
  `app.start_worker_consumers()`; it does **not** serve HTTP.

## 5. End-to-end flow (the "full" pipeline)

```
1. UPLOAD            UI → POST /uploads (multipart CSV)
                     parse_csv_rows() → list of {row_index, company_name, country, firm_id,
                                                  industry, full_address}
2. STATE CREATED     _create_upload_with_rows(): build state.json (status=queued, one row each),
                     persist locally + S3, set gemini_batch.status="waiting_for_rows" (full only)
3. ENQUEUE           publish one RabbitMQ message per row (routing_key singleRA.search.validate)
                     publish failures mark that row failed immediately
4. CONSUME           worker rabbitmq_worker_loop() picks up a message, marks row "processing"
5. PIPELINE (per row)  execute_company_lookup():
                       a. transliterate_inputs_with_gemini (company/address → Latin script)
                       b. classify_address_with_gemini (quality/type of the address)
                       c. parse_city_state_from_full_address_with_gemini (+ heuristic fallback)
                       d. build_investigative_search_queries (phase1..phase4 + industry fallback)
                       e. run_serpwow_search for each query (parallel), collect plausible URLs;
                          dynamically expand with phase5 (people/trade-name/verification) queries
                       f. run_gmaps_from_module (SerpWow places+details) → maybe replace URL
                       g. choose_final_website_with_gemini (confidence scoring) — UNLESS batch
                          post-processing is enabled for this upload
                       h. (full only) run_serpwow_from_codetails + standardize_serpwow_ai_overview
                          _with_gemini → address/phone/email/industry/products/services
                       i. address-alignment guard can null the URL if the mapped address conflicts
6. RAW JSON          upload_serpwow_json_to_s3 (per-row raw response)  → s3_serpwow_json_key
7. ROW WRITTEN       update_row_state(status=completed|failed, result=CrawlResponse.model_dump())
                     If batch post-processing is on, rows that found no URL are kept "completed"
                     with error "Pending Gemini batch post-processing decision."
8. FILE STATUS       persist_upload_state() recomputes status (queued/processing/completed/
                     completed_with_errors); writes output.json once the file is terminal
9. GEMINI BATCH      when status∈{completed,completed_with_errors} and ENABLE_GEMINI_BATCH_
   (full only)       POSTPROCESS=true: maybe_start_gemini_batch_for_upload() queues an asyncio
                     task → run_gemini_batch_for_upload(): builds one request per row, submits
                     batchGenerateContent, polls to completion, rewrites each row's URL +
                     descriptions + firmographics, sets gemini_batch.status="succeeded"
10. DOWNLOAD         UI enables JSON/XLSX links once rows are done AND batch is terminal.
                     GET /uploads/{id}/output?format=xlsx builds the workbook on demand.
```

Pipelines `url_discovery`, `gmaps`, `gsearch` stop after step 7 (no firmographics, no batch).
`firmographics` skips steps a–g entirely and only does step h from a given URL.

## 6. Reliability mechanisms (high level)

- **Idempotency:** before processing, the worker skips a row already `completed`/`failed`
  (`app.py:5928`–5945); `update_row_state` refuses to regress a terminal row back to
  `processing` (`app.py:5585`).
- **Redelivery policy:** a failing job is nack-requeued **once**; on the *redelivered* attempt it
  is dropped and the row marked failed, preventing poison-message loops (`app.py:6126`–6181).
- **Per-job timeout:** `WORKER_JOB_TIMEOUT_SEC` wraps each `process_upload_job` (`app.py:6113`).
- **Queue recovery:** `maybe_requeue_stuck_queued_rows` republishes queued/processing rows when
  the RabbitMQ queue is empty and no rows are active (with a cooldown) (`app.py:5604`).
- **Stale/orphan finalizers:** `maybe_fail_stale_processing_rows` can auto-fail rows stuck in
  `processing`, but only in embedded-worker mode by default (`app.py:5703`).
- **Background S3 writes** with exponential-backoff retry so a slow S3 never blocks the request
  path (`app.py:3896`–3911).
- **Local-first reads/writes:** `/tmp/single_ra_isi` is the fast path; S3 is the durable mirror
  and the cross-process source of truth (`app.py:3886`–3937).

## 7. Important "as-built" caveats

These are real properties of the current code (verified), called out so the docs don't mislead:

- **No browser/proxy crawling in this codebase.** There is no Playwright, no `get_proxy_config`,
  no HTML crawl — the only data source is SerpWow. `massive_proxy_cost_usd` is a per-row
  **conditional** field (designed to carry a proxy/page-load cost that is nonzero only when a URL
  had to be loaded through the Massive proxy); because no proxy/fetch path is wired in here, every
  assignment is the literal `0.0`. The `MASSIVE_*`, `BROWSER_POOL_SIZE`, `USER_AGENT`, and
  `REDIS_*` keys in `.env.example` are correspondingly **not read by `app.py`** in this repo. See
  [02.configuration.md](02.configuration.md) for the exact used/unused split.
- **`analyze_with_gemini` (app.py:1536) is dead code** — defined but never called.
- **Batch-pending row marking is not pipeline-scoped.** The Gemini *batch* runs only for `full`
  uploads (`app.py:5028`), but the worker's "no URL found → mark `completed` with a pending-batch
  note" branch (`app.py:6018`) fires for **any** pipeline whenever `ENABLE_GEMINI_BATCH_POSTPROCESS`
  is on. So enabling the flag for a `url_discovery`/`gmaps`/`gsearch`/`firmographics` upload leaves
  no-URL rows stuck `completed`/pending with no batch to resolve them. Treat the flag as
  `full`-only. (Detail: [05 §4](05.pipelines-and-flow.md), [02](02.configuration.md).)
- **url_discovery still uses Gemini beyond the final-URL chooser:** transliteration always, plus
  address classification + city/state parsing when an address is present (it shares
  `execute_company_lookup` with `full`; only firmographics is skipped). See [05 §6](05.pipelines-and-flow.md).
- **`templates/ui copy.html` is a backup** of an earlier light-themed UI; the app only serves
  `templates/ui.html`.
- The hand-rolled XLSX writer stores **every cell as an inline string** except numbers/bools; it
  does not use shared strings or styling beyond a default font.
