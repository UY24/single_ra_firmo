# 05 · Pipelines & end-to-end flow

This is the "how it actually works" doc. It explains the URL-discovery algorithm phase by phase,
the gates that accept/reject URLs, the firmographics step, the Gemini batch lifecycle, and the
four smaller pipelines.

---

## 1. The search-query phases

The system never crawls websites; it queries **SerpWow** (Google results + AI overview) with a
battery of carefully shaped "dork" queries. Two builders generate these:

- `build_investigative_search_queries` (`app.py:948`) — used by the **full / url_discovery**
  worker pipeline. Always builds phases 1–4 + industry fallback (no explicit no-address branch).
- `build_selected_phase_queries` (`app.py:7096`) — used by the **gsearch** pipeline/endpoint. Lets
  you pick a single phase and has explicit `else` branches for when no address is available.

Both derive inputs first: normalized company name + name variants (`A B C` → also `A.B.C.` and
`ABC`), and address markers extracted from `full_address` — `plot`, `road`, `block`, `house`
(each in hyphen form `Plot-16` and spaced form `Plot 16`), plus `locality`, `city`, `postal`, and
a `location_phrase`.

### The phases (labels are the `attempt`/`phase` values you see in results)

| Phase | Intent | Representative queries (when address present) |
|-------|--------|----------------------------------------------|
| **phase1 — Initial hook & punctuation** | Pin the company to its exact address with quoted markers | `"Acme" "Plot-16" "Road-111" Gulshan Dhaka` · punctuation variant with `Plot 16`/`Road 111` · block variant · `"Acme" "Dhaka 1212"` (city+postal) | 
| **phase2 — AI-overview natural language** | Trigger Google's AI overview synthesis | `What business or trade name operates under "Acme" at Plot 16, Road 111, Gulshan Dhaka?` · `Who is the owner/CEO/MD of "Acme" located in …?` · `What companies are registered at …?` · `Is there a consumer-facing website for Acme registered at …?` |
| **phase3 — Address-only pivot** | Find *anything* at the address, then pivot | `"Plot-16" "Road-111" Gulshan Dhaka -residential` · `"House-16" "Road-111" … company OR business` · block+plot+road |
| **phase4 — Document hunting** | Registry/PDF dorks | `site:.bd "Acme" "Gulshan"` · `filetype:pdf "Acme" "Plot-16" OR "Road-111"` · `filetype:pdf "Plot-16" "Road-111" … directory` |
| **industry_fallback** | When an industry is provided | `What is the official website of "Acme" in the Engineering industry?` |
| **phase5 — Dynamic expansion** *(added at runtime)* | Pivot on entities discovered in earlier results | `"<person name>" "Acme"` · `"<trade name>" "Plot-16" "Road-111"` · `"<trade name>" official website <country>` · candidate-domain verification `"<domain>" "Acme" "<country>"` |

`build_selected_phase_queries` adds **no-address** variants when `full_address` is blank, e.g.
`"Acme" Bangladesh`, `"Acme" official site Bangladesh`, `What is the official website or domain of
"Acme" in Bangladesh?`, `filetype:pdf "Acme" registry OR profile Bangladesh`, and a
`simple_fallback` `Acme Bangladesh`.

Phase 5 is special: it is **not** built up front. During result processing, the worker mines
person names and corporate trade names out of the SerpWow organic/AI titles
(`_extract_phase5_pivots_from_serpwow`, `app.py:890`) and appends new queries, bounded by
`SEARCH_MAX_ATTEMPTS`.

## 2. The acceptance gates (applied to every candidate URL)

A URL must survive **three** gates before it can become the official website:

1. **Blocklist** — `is_disallowed_official_url` (`app.py:1381`): rejects non-http(s), Google,
   social/data-broker/directory domains, file URLs (`.pdf` etc.), document/upload paths.
2. **Plausibility** — `_official_website_looks_plausible` (`app.py:715`): the host must contain a
   meaningful company token (≥4 chars, not generic like "ltd"/"group"), **or** end in the country
   ccTLD *when* meaningful tokens exist.
3. **Address alignment** *(full pipeline, non-batch only)* — `_is_address_aligned` (`app.py:1238`):
   after firmographics, if the mapped address does not contain the input's strong address markers,
   the URL is **nulled** and the row fails with "No reliable official website found with
   address-aligned evidence…" (`app.py:3665`–3691).

The Gemini chooser adds a 4th, model-level check (it can only pick from the candidate set and the
pick is re-validated against gates 1 & 2).

## 3. `execute_company_lookup` — step by step (`app.py:2806`)

This runs for `full` and `url_discovery` rows. `include_firmographics=False` for url_discovery.

```
batch_postprocess_for_upload = (this is an upload row) AND ENABLE_GEMINI_BATCH_POSTPROCESS
                               # when true, the per-row Gemini steps below are SKIPPED and
                               # the batch step does the URL choice + descriptions instead.

(1) Transliterate inputs            transliterate_inputs_with_gemini → working_company_name,
                                    working_full_address (Latin script). Original names are kept
                                    for the response's company_name/input_full_address.
(2) Classify address                classify_address_with_gemini (diagnostic only; recorded in
                                    context.address_classification_ai).
(3) Parse city/state                parse_city_state_from_full_address_with_gemini, guarded against
                                    street-level mis-parses; heuristic fallback if needed.
(4) Build query battery             build_investigative_search_queries(... max=SEARCH_MAX_ATTEMPTS).
                                    If transliteration changed the inputs, also append ONE
                                    "phase0_non_transliterated_probe" using the raw script.
(5) Fire wave 1 (parallel)          run_serpwow_search for each query via a shared httpx client.
                                    Each result → _process_serpwow_attempt_result (inner closure):
                                      • accept the first plausible official_website
                                      • collect all plausible candidates
                                      • record a search_attempts[] entry
                                      • mine phase-5 pivots and APPEND new queries
(6) Fire wave 2 (phase 5)           run the dynamically-added phase-5 queries (parallel), same
                                    processing but no further expansion.
(7) GMaps enrichment                if ENABLE_GMAPS_FALLBACK: run_gmaps_from_module. Add the gmaps
                                    URL as a candidate. Replace the chosen URL with the gmaps URL
                                    when: no URL yet, OR (PREFER_GMAPS_WEBSITE and the gmaps domain
                                    differs and the serp domain isn't plausible).
(8) Dedupe candidates               unique, allowed candidate_urls list.
(9) Final URL chooser (LLM)         if ENABLE_FINAL_URL_GEMINI and NOT batch_postprocess_for_upload
                                    and candidates exist: choose_final_website_with_gemini. The
                                    pick must be in the candidate set and plausible, else ignored.
── early exits ──
(10a) No URL found                  build a failed CrawlResponse (official_website=null) with full
                                    cost breakdown + context; return.
(10b) include_firmographics=False   build a success CrawlResponse (URL only), PIPELINE_URL_DISCOVERY
                                    context; return.
(11) Firmographics                  if NOT batch_postprocess_for_upload: run_serpwow_from_codetails
                                    on the URL → standardize_serpwow_ai_overview_with_gemini →
                                    address/phone/email/industry/products/services.
(12) Address-alignment guard        if mapped address conflicts with the input address → null the
                                    URL, clear firmographics, fail with an explanatory summary.
(13) Assemble response              CrawlResponse with summed serpwow_cost (search + codetails +
                                    gmaps request counts) and gemini_cost (all per-row calls),
                                    plus the full context tree. Return (response, raw_json).
```

**When batch post-processing is enabled** for the upload, steps (2)-(8) still run (they produce the
search evidence the batch prompt needs), but the per-row Gemini URL chooser (9) and firmographics
(11) are skipped — the batch step performs the URL decision and writes the bilingual descriptions.
A row that finds no URL in steps (5)-(8) is still marked **`completed`** (not failed) with
`error="Pending Gemini batch post-processing decision."` so the batch gets a chance to decide
(`app.py:6014`–6024).

## 4. Worker → row status (`process_upload_job`, `app.py:5905`)

```
idempotency: skip if row already completed/failed
mark row "processing"
dispatch by pipeline:
   firmographics → execute_firmographic_extraction
   gmaps         → execute_gmaps_lookup
   gsearch       → execute_gsearch_lookup_for_worker(phase=…)
   else          → execute_company_lookup(include_firmographics = pipeline != url_discovery)
upload per-row raw JSON to S3  → s3_serpwow_json_key (also stored as s3_html_key alias)
result = CrawlResponse.model_dump() + s3 keys
decide status:
   official_website present                       → completed
   else if ENABLE_GEMINI_BATCH_POSTPROCESS        → completed (error="Pending … batch decision")
   else                                           → failed ("Official website not found; …")
update_row_state(...)
```

`persist_upload_state` then recomputes the file-level status and, when terminal, writes
`output.json` and calls `maybe_start_gemini_batch_for_upload`.

> **⚠ The "else if ENABLE_GEMINI_BATCH_POSTPROCESS" branch (`app.py:6018`) is NOT pipeline-gated.**
> It marks *any* no-URL row `completed`+pending regardless of pipeline, even though the batch that
> would resolve it (`maybe_start_gemini_batch_for_upload`) runs **only for `full`** uploads
> (`app.py:5028`). With the flag on, a no-URL row in a `url_discovery`/`gmaps`/`gsearch`/
> `firmographics` upload therefore ends `completed` with a "pending batch" note that nothing ever
> resolves — and its `failed` count stays 0, masking the miss. In practice, enable the flag only
> for `full`.

## 5. Gemini batch lifecycle (full pipeline only)

Triggered automatically when a `full` upload reaches `completed`/`completed_with_errors` and
`ENABLE_GEMINI_BATCH_POSTPROCESS=true`.

```
maybe_start_gemini_batch_for_upload (app.py:5027)
    guards: pipeline==full, batch enabled, status terminal, not already queued/running/succeeded,
            not already an in-flight task
    → set gemini_batch.status="queued"; create asyncio task run_gemini_batch_for_upload

run_gemini_batch_for_upload (app.py:4704)
    1. lock → set status="running" (reuse existing job_name/started_at); if already "succeeded" return
    2. build one request per completed/failed row (_build_batch_requests_for_state)
         - no rows → status="skipped", return
    3. if no existing job_name: write batch_input_jsonl artifact, create the job
         (_gemini_batch_create_sync → display_name "single-ra-upload-<id>-<uuid>"); record job_name
       else: resume polling the existing job_name
    4. poll every GEMINI_BATCH_POLL_SEC up to GEMINI_BATCH_TIMEOUT_SEC, tolerating transient errors,
       until _gemini_batch_is_terminal
    5. write batch_output_json artifact; if not success → raise (status becomes "failed")
    6. map inlined responses back to rows: by metadata.key "row-N", with positional fallback when
       counts match; parse each response's JSON
    7. for each mapped row: re-validate the chosen URL (blocklist + plausibility), set
       official_website (or null), summary, website_company_descirption_ai / _translated_ai,
       address/phone/email/industry/products/services, and ADD the batch token cost to
       gemini_cost_usd / total_cost_usd / cost_breakdown.gemini_batch_cost_usd; set row status
       completed/failed; record context.gemini_batch_ai
    8. set gemini_batch.status="succeeded" with usage + batch_cost_usd; persist
    (finally) remove the task from gemini_batch_tasks
```

**Status reconciliation & resume** (driven by `GET /uploads/{id}/status` and
`/failure-analysis`):
- `maybe_resume_gemini_batch_for_upload` (`app.py:5049`) re-attaches a polling task if a job is
  `running` with a `job_name` but no live task (e.g. after an API restart).
- `maybe_reconcile_gemini_batch_status` (`app.py:5067`) fetches the live Gemini job state, maps it
  via `_derive_ui_batch_status`, and persists any change. It also **auto-fails** a job stuck in
  `running` with no `job_name` for longer than `GEMINI_BATCH_STARTUP_TIMEOUT_SEC`.

The brief's bilingual-description rules (≥250 chars, ASCII English, country-language original,
no links/citations/hedging, `–` when nothing meaningful) are encoded in the batch prompt
(`_build_batch_prompt_for_row`, `app.py:4314`–4350).

## 6. The four non-full pipelines

| Pipeline | Executor | What it does | Gemini? | Firmographics? | Batch? |
|----------|----------|--------------|---------|----------------|--------|
| **url_discovery** | `execute_company_lookup(include_firmographics=False)` | Steps 1–10b: find the URL, stop. | **transliteration always** (`app.py:2846`); **address classification + city/state parse when an address is present** (`2891`/`2929`); **final-URL chooser** (`3371`, unless the upload has batch enabled). Only firmographics (the codetails AI-overview mapping) is skipped vs. `full`. | no | no |
| **firmographics** | `execute_firmographic_extraction` | Given a URL, run codetails SerpWow AI-overview → map to firmographic fields; warn if address misaligned. | mapping only | yes (the whole point) | no |
| **gmaps** | `execute_gmaps_lookup` | One SerpWow GMaps query; take website/address/phone/category from the best place. | no | partial (from maps) | no |
| **gsearch** | `execute_gsearch_lookup_for_worker(phase)` | Run one chosen search phase's queries; return the first plausible candidate. Diagnostic. | no | no | no |

Only `full` ever runs the Gemini batch. `firmographics` uploads are gated for download without the
batch (`useBatchGate:false` in the UI).

## 7. Cost accounting

Every per-row result reports four cost numbers (and a `cost_breakdown` sub-tree):

- `serpwow_cost_usd` = total SerpWow requests (search + codetails + gmaps) × `SERPWOW_USD_PER_REQUEST`.
- `gemini_cost_usd` = sum of token costs from transliteration + address classification +
  city/state parse + final-URL chooser + serpwow-mapping; the **batch** step later adds its
  per-row token cost on top.
- `massive_proxy_cost_usd` = `0.0` (vestigial).
- `total_cost_usd` = serpwow + gemini.

> Caveat: the **gsearch** executor uses a flat `0.02`/query placeholder for `serpwow_cost_usd`
> rather than `calculate_serpwow_cost_usd` (`app.py:2486`), and `gmaps.py`'s internal SerpWow cost
> counter (driven by `SERPWOW_USD_PER_SEARCH`) is **not** merged into the reported costs. Treat
> reported costs as approximate.

## 8. Reliability flow (recovery & finalizers)

`GET /uploads/{id}/status` is the heartbeat that drives most recovery:

```
status endpoint:
  maybe_resume_gemini_batch_for_upload        # re-attach batch poller if needed
  maybe_reconcile_gemini_batch_status         # sync batch status from Gemini
  maybe_requeue_stuck_queued_rows             # republish stuck rows if queue empty & idle
  maybe_fail_stale_processing_rows            # auto-fail stale/orphaned rows (embedded mode)
  summarize_upload_state → return
```

- **Queue recovery** (`app.py:5604`): only acts when the RabbitMQ queue depth is 0 **and** no rows
  are active **and** the cooldown has elapsed; republishes `queued`/`processing` rows; rows whose
  republish fails are marked `failed`.
- **Stale finalizer** (`app.py:5731`): fails `processing` rows older than
  `PROCESSING_STALE_TIMEOUT_SEC`. Default-on only in embedded-worker mode (in split mode the API
  can't see the worker's active set, so it stays off to avoid mass false-failures).
- **Orphan finalizer** (`app.py:5760`): fails `processing` rows when no worker task is active for
  the upload, past `ORPHAN_UPLOAD_FINALIZE_TIMEOUT_SEC`. Off by default; requires embedded mode.
- **Manual retry**: `POST /uploads/{id}/retry-failed-rows` re-queues failed/queued/processing rows
  and (for full uploads) resets `gemini_batch` to `waiting_for_rows`.
