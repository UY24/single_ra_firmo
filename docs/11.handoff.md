## TL;DR

`website_url_finder` (repo `single_ra_firmo`, service name **Single RA ISI**) is a FastAPI +
RabbitMQ batch system that, given a CSV of companies, finds each company's **official website
URL** and produces firmographics (address/phone/email/industry/products/services) and a bilingual
**business description** (country language + English). It implements `AI descriptions
requirements.pdf`. The **only external data source is SerpWow** (Google search results, AI
overviews, and Google Maps). **Gemini** is the LLM used to prep inputs, pick the final URL, and
clean SerpWow data into structured fields. State lives in `state.json` (local `/tmp` + S3 mirror);
work is dispatched one RabbitMQ job per company row to a separate worker process.

## Current status (as found)

- Single commit (`b714f0d "first commit"`), branch `main`, remote `github.com/UY24/single_ra_firmo`.
- Runs as **two processes**: `python app.py` (API/producer + UI + batch driver) and
  `python worker.py` (consumer that does the work). Embedded single-process mode via
  `ENABLE_EMBEDDED_WORKER=true`.
- No `requirements.txt` / `Dockerfile` / `config.yaml` / tests in the repo.
- There is a sample completed run in `input.json` (124 companies, all succeeded) — the best
  reference for the real output shape.

## Architecture in 6 lines

1. UI / `POST /uploads` → parse CSV → write `state.json` → publish 1 RabbitMQ msg per row.
2. Worker consumes a msg → runs the pipeline for that company → writes the row result back to state.
3. Pipeline = SerpWow search (+ Google Maps) → candidate URLs → Gemini picks the official URL →
   SerpWow firmographics → Gemini cleans them.
4. When all rows of a `full` upload finish → optional **Gemini batch** rewrites every row's URL +
   descriptions in one big call.
5. State is local-first (`/tmp/single_ra_isi/<id>/`) and mirrored to S3; the UI polls
   `/uploads/{id}/status`.
6. Five pipeline modes select which `execute_*` runs: `full`, `url_discovery`, `firmographics`,
   `gmaps`, `gsearch`. (Details: [01](01.overview-and-architecture.md), [05](05.pipelines-and-flow.md).)

## ★ Gemini LLM call map (answers "after which services do we clean data with the LLM?")

**Short answer:** SerpWow returns raw/messy data; we use Gemini to *clean/decide* in some places
but **not** for Google Maps. Specifically:

| Stage / data source | Cleaned by an LLM? | Which call | When it runs |
|---|---|---|---|
| **Input** company name + address (before any search) | — (transform, not cleanup) | `transliterate_inputs_with_gemini` (`app.py:2849`), `classify_address_with_gemini` (`2893`), `parse_city_state_from_full_address_with_gemini` (`2933`) | Start of `execute_company_lookup`, **before** SerpWow. Prep the inputs/queries. |
| **SerpWow search** results (the URL hunt) | Indirectly — Python first, then one LLM decision | URLs are extracted/filtered by **Python** (`_extract_official_website_*`, blocklist, plausibility). The aggregated candidates + raw search response are then handed to **`choose_final_website_with_gemini`** (`app.py:3371`) which picks the official URL with a confidence score. | **After** all SerpWow search waves + after GMaps. Skipped if Gemini-batch post-processing is enabled. |
| **SerpWow Google Maps** (places/place_details) | **No LLM** | `_select_best_gmaps_website` (`app.py:1300`) + `extract_gmaps_website` — **pure Python scoring**. Its chosen URL just becomes another candidate for `choose_final_website_with_gemini`. | During the GMaps enrichment step. No Gemini touches GMaps data directly. |
| **SerpWow AI-overview** for the chosen domain (firmographics) | **Yes** | **`standardize_serpwow_ai_overview_with_gemini`** (`app.py:3631` in full; `2729` in the firmographics pipeline) — turns the messy AI-overview text into structured `{address, phone, email, industry, products[], services[]}`. | **After** `run_serpwow_from_codetails` returns the AI overview. Skipped if Gemini-batch post-processing is enabled. |
| **End of `full` upload** (all rows done) | **Yes — the big one** | **Gemini batch** (`run_gemini_batch_for_upload`, `app.py:4704`) takes each row's full accumulated SerpWow/GMaps/search context and produces the final URL + the bilingual ≥250-char descriptions + firmographics in one `batchGenerateContent` call. | Once per upload, after rows are terminal, if `ENABLE_GEMINI_BATCH_POSTPROCESS=true`. |

**Ordering for one `full` row (non-batch mode):**
```
transliterate → classify addr → parse city/state          [LLM on INPUTS]
   → SerpWow search ×N (Python extracts candidates)        [no LLM per call]
   → GMaps via SerpWow (Python picks best, no LLM)
   → choose_final_website_with_gemini (candidates+raw)     [LLM: pick URL]
   → SerpWow codetails AI-overview for the domain
   → standardize_serpwow_ai_overview_with_gemini           [LLM: clean firmographics]
```

**Two important rules:**
- When **`ENABLE_GEMINI_BATCH_POSTPROCESS=true`**, the per-row `choose_final_website_with_gemini`
  **and** `standardize_serpwow_ai_overview_with_gemini` are **skipped** — the end-of-upload batch
  does the URL choice + firmographics + descriptions instead (so you don't pay for both).
- The **`gmaps`** and **`gsearch`** pipelines use **no Gemini at all** — they're pure SerpWow +
  Python. So Google-Maps location data is **never** LLM-cleaned in those standalone modes; it's
  only LLM-influenced in `full`/`url_discovery` because the GMaps URL becomes a candidate the
  URL-chooser LLM sees.
- **`url_discovery`** shares `execute_company_lookup` with `full`, so it runs the **same per-row
  Gemini calls minus firmographics**: transliteration (always) + address classification +
  city/state parse (when an address is present) + the final-URL chooser. It just skips the
  `standardize_serpwow_ai_overview_with_gemini` firmographics step and never triggers a batch.

So: *yes, we use Gemini to clean SerpWow data — after the **search** (URL decision) and after the
**codetails AI-overview** (firmographic fields), plus the **batch** at the end — but **not** after
the Google Maps lookup, which is cleaned heuristically in Python.*

## Cost model (and a correction worth knowing)

Each row reports `serpwow_cost_usd`, `gemini_cost_usd`, `massive_proxy_cost_usd`, `total_cost_usd`.

- `massive_proxy_cost_usd` is a **conditional** per-row field: by design it would be nonzero only
  when a URL had to be loaded through the Massive proxy. **In this codebase there is no
  proxy/page-fetch path**, so every assignment is the literal `0.0`. If a proxy/page-load layer is
  reintroduced, this is the field it should populate (and `MASSIVE_*` env keys would start mattering).
- `serpwow_cost_usd` = total SerpWow requests × `SERPWOW_USD_PER_REQUEST`. Caveat: the `gsearch`
  executor uses a flat `0.02`/query placeholder, and `gmaps.py`'s own cost counter
  (`SERPWOW_USD_PER_SEARCH`) is not merged in. Treat reported costs as approximate.
- `gemini_cost_usd` = sum of per-row Gemini token costs; the batch adds its share afterward.

Details: [05 §7](05.pipelines-and-flow.md).

## How to run (fast path)

```bash
python -m venv .venv && source .venv/bin/activate
pip install fastapi uvicorn aio-pika boto3 httpx aiohttp pydantic python-dotenv pyyaml pandas openpyxl
cp .env.example .env   # fill SERPWOW_API_KEY, GEMINI_API_KEY, RABBITMQ_*, (optional) S3_*/AWS_*
# terminal 1:
python app.py          # UI at http://localhost:<port>/ui  (code default 11500; .env example 14000)
# terminal 2:
python worker.py
```

## Known caveats / gotchas / risks

1. **Nothing processes without a worker.** Uploads sit `queued` until `worker.py` (or embedded
   worker) runs.
2. **`.env` blank values override defaults.** `RABBITMQ_USER=` (empty) becomes `""`, not `guest`.
   Fill fields or omit the line. ([02](02.configuration.md))
3. **Code defaults ≠ `.env.example`** for several timeouts/ports (`API_PORT` 11500 vs 14000,
   `WORKER_JOB_TIMEOUT_SEC` 600 vs 1800, `PROCESSING_STALE_TIMEOUT_SEC` 300 vs 1500, S3 timeouts).
   Set them explicitly if you care.
4. **`.env.example` lists many keys nothing reads** (`MASSIVE_*`, `BROWSER_POOL_SIZE`,
   `USER_AGENT`, `REDIS_*`, `OUTPUT_PREFIX`, `SEARCH_FETCH_ATTEMPTS`, `ENABLE_ADDRESS_FALLBACK`).
   See [02 §B](02.configuration.md). Don't assume Redis/proxy/browser exist — they don't, here.
5. **No `config.yaml`** → `gmaps.py` returns the *entire* place_details (no field filtering) and
   relies on regex postal heuristics for country detection.
6. **Dead code:** `analyze_with_gemini` (`app.py:1536`) is never called. `templates/ui copy.html`
   is not served.
6a. **`ENABLE_GEMINI_BATCH_POSTPROCESS` is effectively `full`-only — but the row marking isn't
   gated.** The batch runs only for `full` (`maybe_start_gemini_batch_for_upload`, `app.py:5028`),
   yet the worker's "no URL → mark `completed` with a pending-batch note" branch (`app.py:6018`)
   fires for **any** pipeline when the flag is on. So turning it on for a
   `url_discovery`/`gmaps`/`gsearch`/`firmographics` upload leaves no-URL rows stuck
   `completed`/pending (and `failed`=0, masking misses) with no batch to resolve them. Enable it
   only for `full`.
6b. **The two batch-recovery scripts are broken as-shipped.** Both reference `app.upload_lock`,
   which doesn't exist (`app` has `upload_locks` + `get_upload_lock(upload_id)`, `app.py:54`).
   `requeue_wait_and_push_remaining_to_gemini_batch.py:183` is on the main path → it `AttributeError`s
   *after* submitting/polling the Gemini batch but before saving results (wasted batch);
   `push_processed_rows_to_gemini_batch.py:79` only fails on `--force-new-job`. One-line fix each:
   `async with app.get_upload_lock(upload_id):`. ([08](08.supporting-modules-and-scripts.md))
7. **Split-process finalizers off by default.** Stale/orphan auto-fail only run in embedded mode,
   because the API can't see the worker's in-memory active-row set across processes. Recovery in
   split mode leans on `maybe_requeue_stuck_queued_rows` (queue-empty + idle + cooldown).
8. **`/tmp` is the local store.** Without `S3_BUCKET`, a `/tmp` wipe loses all uploads.
9. **Misspelled keys are intentional:** `website_company_descirption_ai` /
   `…_translated_ai` ("Descirption") come from the brief and are used everywhere — don't "fix"
   them or mapping breaks. ([03](03.data-models.md))
10. **Synchronous `/crawl` runs the whole pipeline in-request** — can be slow; it's for testing.

## Suggested next steps / open questions

- **Fix the two batch-recovery scripts** (`push_processed_rows_to_gemini_batch.py:79`,
  `requeue_wait_and_push_remaining_to_gemini_batch.py:183`): `app.upload_lock` →
  `app.get_upload_lock(upload_id)` (they `AttributeError` otherwise).
- **Pipeline-gate the batch-pending marking** (`app.py:6018`) so non-`full` pipelines don't strand
  no-URL rows as `completed`/pending; or restrict `ENABLE_GEMINI_BATCH_POSTPROCESS` to `full` at
  upload time.
- Add a `requirements.txt`/lockfile + a smoke test; pin the Python version (3.12).
- Decide whether the proxy/browser layer is coming back; if not, prune the dead `MASSIVE_*`/proxy
  scaffolding and the `massive_proxy_cost_usd` field, or wire it up.
- Reconcile the cost placeholders (`gsearch` 0.02/query; gmaps counter not merged).
- Confirm SerpWow rate limits vs. `WORKER_CONCURRENCY` × `SEARCH_FETCH_CONCURRENCY` for big batches.
- Consider persisting `output.json` incrementally (currently only on terminal status) if partial
  downloads are needed.
